## TL;DR

Claude Code 對非開發者最大的價值，不是它會寫程式，而是它把「跨檔案的專案脈絡」當作一等公民——只要把規則寫進 CLAUDE.md、把按需用的能力拆成 Skills，再用 Hooks / Subagents / MCP 補上自動化、並行與外部連線，就能用自然語言把一個小想法做成可用的 App。

- **CLAUDE.md 是寫給 AI 的備忘錄**：每次新對話自動載入，解決「上一次對話的記憶不會延續」與「Claude 不會主動讀所有檔案」這兩個一般使用者最容易踩到的坑。
- **Skills 是按需載入的能力包，但不是裝越多越好**：每個 Skill 只在被判斷相關時才載入，能省上下文；但安裝一堆品質參差的 Skills 反而會讓 Claude 花更多時間篩選，少而精勝過貪多。
- **Hooks 是「規則明確就不要交給 AI」的選擇**：條件式自動執行、百分之百觸發，把 AI 該做判斷的力氣留給真正需要判斷的事。
- **Subagents 把線性對話變成可並行的分工**：臨時的一次性分身做平行搜集，常駐 `/agents` 則做可重用的專職角色。
- **MCP 是 AI 的 USB 接口**：要連 Notion、Email、行事曆這類外部工具，貼個官方頁面網址請 Claude 代裝即可，幾乎不用碰設定。
- **Vibe Coding 的成敗在前期規劃**：先切到 Opus + Plan Mode，把需求講清楚、要求 Claude 不足之處先反問，再核准計畫進入實作；遇錯就把錯誤訊息或截圖貼回去，由 Claude 修，循環推進。

## 1. 安裝 Claude Code 與 VS Code 整合 (00:00)

Claude Code 是一款 AI 程式開發助手，但定位上其實是「即使不懂任何程式語言，也能透過對話請它打造想要的生產力工具」。安裝路徑因系統略有不同：Windows 因為 Claude Code 需要 Git 來追蹤程式碼變動，必須先裝 Git（下載、雙擊、一路下一步），再開 PowerShell 把官網提供的 Windows 指令貼上執行；Mac 則可以跳過 Git，直接用 Spotlight 開 Terminal，貼上 Mac 對應的指令即可。

裝好之後，雖然可以直接在終端機跑 `claude`，但對非開發者來說更友善的做法是再裝一套 VS Code：建立一個專案資料夾，把 VS Code 的工作範圍指向它，再從選單「新增終端」、輸入 `claude` 啟動。首次啟動會問顏色主題、使用方式（一般使用者最建議的起點是每月 20 美元的 Pro 方案，授權會自動導到瀏覽器），並會在 VS Code 內安裝對應的擴充功能；如果沒自動裝，到左側「延伸模組」搜「Claude」手動裝也行。擴充功能比純文字介面多了圖形化的側邊欄面板，對初學者門檻明顯較低。

Claude Code 內建三種模型——Haiku、Sonnet、Opus，輸入斜線 `/` 選 Switch Model 就能依任務切換。這條安裝線的重點不在指令本身，而在於：作者刻意把 GUI（VS Code 擴充）放在 CLI 前面，因為後續所有的「授權對話框」、「側邊欄反白」、「歷史記錄分支」這些對非開發者很關鍵的視覺操作，都要靠 VS Code 的介面才看得到。

## 2. 基本操作：對話、跨檔案脈絡與授權 (03:31)

對話框就是聊天介面——直接輸入文字，`Shift+Enter` 換行、`Enter` 送出；右上角的 `+` 開新對話，左側下拉選單能瀏覽、重新命名歷史對話。真正的重點不在這些按鈕，而在 Claude Code 怎麼看待「專案」。作者用一個短篇冒險故事的例子來示範：在專案裡建一份 `角色.md` 記角色設定，另建一份 `故事.md` 放正文，讓設定與劇情各自獨立。把這兩份檔案丟給 Claude 檢查時，它很快就指出主角人設與情節有矛盾並提出修改建議——這就是 Claude Code 的強項：能理解跨檔案的內容脈絡，以全局視角掌握專案中的關鍵資訊。

它不只是「看」，還很擅長「動手」：可以直接請它修改情節，不必自己改。但任何編輯或新建檔案都會先跳出授權提示，只有使用者按 Yes，變更才會寫入。對話中要叫出某份檔案有兩個技巧：`@檔名` 會把該檔讀進這次對話的上下文；或者在文件中直接反白一段文字，內容會自動帶進側邊欄的輸入框，方便請 Claude 針對該段做改寫或修正。

如果覺得每次授權太煩，可以按「允許所有編輯」或把編輯模式改成「自動編輯」，後續 Claude 繼續寫時就不再跳框。執行到一半發現提示詞錯了，最快的做法是按 `ESC` 立即中斷，不必等它跑完。這一節的隱性訊息是：Claude Code 的協作節奏是「指令—授權—變更—測試」的小步迭代，而不是把整個專案丟給 AI 然後等結果。

## 3. CLAUDE.md：寫給 AI 的備忘錄 (07:39)

承上一節的故事範例，作者插入一行小標題請 Claude 介紹「小花」這個角色，結果 Claude 把小花寫成開朗活潑的女孩——跟 `角色.md` 裡的設定完全相反。這個看似 bug 的現象，剛好點出了 Claude Code 兩個關鍵特性：

第一，**Claude 在上一次對話中的記憶不會自動延續到新的對話**。第二，**在同一個對話中，為了節省上下文容量，Claude 不會每次都讀取專案裡的所有檔案**，而是依任務需求自行判斷哪些檔案可能相關，再選擇性讀取。所以小花跑掉，不是 Claude 忘了設定，而是它根本沒把 `角色.md` 放進這次的上下文。

解法有兩個：每次下指令前手動提醒 Claude 先讀 `角色.md`；或者建立一份名為 `CLAUDE.md` 的文件。後者的特別之處在於——Claude 每次執行任務前都會仔細讀取裡面交待的事項，等同是寫給 AI 的備忘錄。作者把原本的 `角色.md` 直接改名為 `CLAUDE.md`，重送同一個提示詞，這次 Claude 在思考過程中就會先參考 `CLAUDE.md` 的人設內容，小花的個性也就回到原先設定的內向。CLAUDE.md 真正好用的地方，是只要想到什麼「每次都應該遵守」的事項，都可以隨時補進去——例如「小標題是用來引導故事走向」的規則。寫好之後，下一次測試 Claude 就會照標題的暗示鋪陳氣氛、推動劇情，不必每次都在提示詞裡重複提醒。

## 4. 中斷與還原：ESC 與三種 Fork (09:41)

除了 ESC 中斷之外，如果發現故事走偏了，可以把它退回到較早的時間點。Claude Code 在每次互動點都提供三個還原選項：**Fork Conversation from here** 只還原「對話」、檔案保持現狀；第二個剛好相反，「檔案」還原但對話完整保留；第三個則把對話和檔案一起倒轉回那個狀態。

這個還原機制不是覆蓋而是「分支」——就像在一棵樹上長出新樹枝，原本的樹幹不會消失。所以隨時可以透過上方的歷史記錄選單跳回主線，不用擔心反悔的機會被吃掉。這個設計讓 Vibe Coding 的試錯成本很低：不喜歡的分支隨手切就好，主線永遠在。

## 5. Skills：按需載入的能力包 (10:25)

CLAUDE.md 雖然好用，但專案越複雜、規則越多，它會跟著膨脹，帶來兩個現實代價：一是新對話一開始就占掉一大塊上下文空間；二是當 Claude 在執行特定任務時，CLAUDE.md 裡太多不相關的規則反而會分散注意力，讓它更難專注在眼前的目標。

更理想的做法是把「不是每次都會用到」的規則和流程，從 CLAUDE.md 拆出來變成 **Skill**。Skill 與 CLAUDE.md 最大的不同，是它「需要用到的時候」才會載入——能省更多上下文，也讓工作流程更穩定。要找現成的 Skill，到 GitHub 搜 `Claude Code Skills` 即可找到許多社群整理的能力包；Anthropic 自己也維護一個公開的 GitHub 入口，放了不少官方與半官方範例。

安裝這件事被作者刻意做得「賴皮」：完全不用研究步驟，把目標頁面的網址複製、回到 VS Code 貼上、請 Claude 代為安裝就好；過程中如果需要特殊套件，也是請 Claude 一條龍幫忙裝完。Skill 安裝到專案後，會在側邊欄出現對應的 `SKILL.md`，裡面寫了技能名稱、摘要說明與工作流程。執行任務前，Claude 會先讀每個 Skill 的名稱與摘要，看與任務是否相關；相關才會照裡面的指示執行。

作者示範了兩個 Skill 的組合使用：先裝官方 `pptx`（教 Claude 做投影片），再到 GitHub 找一個維護狀況正常的 Nano Banana Skill 裝起來（要 Gemini API 金鑰，到 Google AI Studio 拿）。然後丟一個複合任務：依目前的故事情節做三頁 PPT，並用 Nano Banana 生成像童書風格的背景。Claude 會自動參考這兩個 Skill 來完成任務；成品的視覺與文字旁白都自然，只是角色一致性還需要調 Nano Banana 的提示詞。

除了裝別人的，也可以裝 **Skill Creator** 這個特殊的「建立技能的技能」，讓 Claude 帶著你做一個專屬 Skill——作者建了一個「在段落結尾生成三個劇情分支讓我選」的小技能，按提示回答幾個問題就完成。但章節最後有個重要的提醒：**有些人為了讓 Claude 更厲害而裝一堆 Skills，這可能適得其反**——品質參差、功能重複，反而讓 Claude 花更多時間篩選。比較理想的做法是只保留少量優質、架構清晰的 Skills。

## 6. Hooks：規則化的自動觸發 (16:09)

Skills 雖然好用，但如果手上的規則本來就很明確、條件也很簡單（「當某個事件發生時，就固定做某件事」），把這種流程交給 AI 來判斷反而是浪費運算資源。這時更適合用 **Hooks**。

Hooks 的優點是一旦設定好條件，它就**百分之百一定會執行，不依賴 AI 的自由心證**。作者示範的例子是建一個 Hook：當 Claude 完成交辦的任務時，系統自動發一個桌面通知。送出「續寫 300 個字」的指令後可以離開去做別的事，等 Claude 寫完，桌面通知會立刻彈出。這個分工的隱含原則是：判斷留給 AI，鐵律留給 Hook。

## 7. Subagents：並行分工與常駐分身 (16:57)

一般跟 AI 互動是線性的——丟一個問題、等它答完、再換下一題，就像一間醫院只有一個診間。Claude Code 用 **Subagents** 打破這種流程：可以把工作拆開、委託給不同的 AI 小幫手，讓多項任務並行。

作者示範請 Claude 上網蒐集故事素材並把任務分派給兩個小幫手，各自負責一個主題；兩個任務同時展開，結束後各自回報，最後由 Claude 統整再回傳。同樣的時間能拿到更完整的資訊。

但這種臨時生成的小帮手是「一次性」的——任務結束就被系統回收。如果希望有個能跨任務反覆使用的常駐分身，要用 `/agents` 指令進入終端機的設定流程，依序回答：Agent 層級（Project 表示存在此專案內）、建立方式（讓 Claude 協助設定最簡單）、定位描述（如「專門負責故事角色的建立」）、工具權限（如「讀取」「編輯」）、AI 模型（Sonnet 兼顧效能與成本）、辨識顏色（多 Agent 並行時用顏色分辨誰在做事），最後啟用記憶。建好後，Claude 通常會自動把適合的任務派給合適的小幫手；也可以用 `@小幫手名` 直接點名，省去判斷力氣。

## 8. MCP：外接工具的 USB 接口 (19:15)

如果小幫手可以上網查資料，能不能順便檢查 Email、看一下行事曆？預設不行——但裝了 **MCP** 就可以。MCP 在作者的比喻裡是「AI 的 USB 接線」：當 AI 需要連到外部工具（Notion、Email、行事曆等）時，由 MCP 提供標準化的接口。

示範流程依然是賴皮路線：要讓 Claude 管理 Notion 筆記，到網路上搜 `Notion MCP`，進到官方說明頁，把網址貼回 VS Code 請 Claude 安裝。裝完重啟 Claude Code，輸入 `/MCP` 就能在伺服器清單看到剛裝的 Notion MCP；點「驗證」，再到瀏覽器完成授權即可。測試時請 Claude 把 `故事.md` 的內容拷貝到 Notion 筆記，等於專案資料夾之外多了一個保存點。

MCP 的生態其實很像 Skills——一旦知道想接什麼服務，就用關鍵字找現成的伺服器或範例專案，交給 Claude 處理連線設定。同樣的「找—貼—請 Claude 裝」三步走。

## 9. 上下文與帳號用量管理 (20:42)

走到這裡，影片裡示範對話的用量已達 64%。當數值太高時，Claude 的表現會變得不穩定，容易忘記過去的對話或犯下更多錯誤。建議在用量達到 70 到 80% 時主動用 `/compact` 把舊對話內容壓縮一次，或乾脆對新任務直接開一個新對話。

除了單一對話的上下文長度之外，**帳號本身的用量**也要留意：輸入 `/account` 可以看到目前剩餘額度與下一次重設的等待時間。常跑大型、複雜專案的人可以考慮升級 Max 方案以取得更高用量上限。這節的訊息很短，但放在這個位置是有意義的——它把前面所有「能力擴充」的論述拉回現實：再強的 AI 也吃資源，要長期協作就得學會管理它。

## 10. Vibe Coding 實戰：Chrome 翻譯擴充 (21:30)

收尾的實作示範是一個典型的 Vibe Coding 起點：看英文 YouTube 影片時遇到不認識的單字、但字幕沒辦法反白查詢——那就用 Claude Code 開發一個有 OCR 文字辨識的翻譯工具。

**前期準備**有幾個關鍵設定：建一個專案資料夾、把 VS Code 工作範圍切過去；用 `/model` 把 AI 切成 Opus（擅長處理複雜邏輯推理與架構設計）；確認「思考模式」已啟用，並依專案複雜度調整推理深度；如需要可以 `/plugins` 看看有沒有合用的外掛——所謂外掛其實就是把 Skills、Subagents、Hooks、MCP 打包成可攜的懶人包，例如 Frontend-Design 就很適合做 UI 的專案。

**規劃階段最忌諱的，就是在需求還很模糊的時候就讓 Claude 開始蓋房子**。比較穩妥的做法是切到 **Plan Mode**，把需求整個交代清楚（這個 App 想解決什麼問題、核心功能有哪些），並在文末加上：「如果有資訊不足的地方需要我說明，請先詢問我」。Claude 讀完後通常會反問幾個關鍵問題，補齊模糊處；牽涉技術選型時還會主動給一個推薦方案，讓沒程式背景的使用者也能輕鬆決定。計畫拿出來後，從頭看一遍、按「同意」，Claude 才依核准的藍圖進入實作。

**測試與迭代**走的是一條穩定的循環：擴充功能做好後，照 Claude 寫的步驟測試——打開瀏覽器的擴充功能頁、啟用開發人員模式、載入未封裝項目指向專案資料夾、把 Gemini API Key 貼進去。出錯時不用緊張，這是 Vibe Coding 中很常見的現象，只要把錯誤訊息拷貝下來或截圖貼回 VS Code 請 Claude 修就行。Claude 改完會請你再測一次，這次驗證通過，就請它做下一個功能。如果某些步驟需要使用者親手操作（例如把 App 部署到雲端、上傳到 GitHub），就請 Claude 把詳細操作列出來照做。

**收尾的工程紀律**：功能跑起來後，把專案納入 Git 版本控制，後續若新功能出問題能還原到穩定版；輸入 `/init` 讓 Claude 分析所有檔案，把該注意的事項記到 CLAUDE.md，之後開新對話時 Claude 能更快掌握專案架構與規範。最後再示範新增「以字母／建立日期／隨機」三種排序方式給單字本——只要把需求講給 Claude，它就會改對應的程式碼，改完手動測，每改一個功能就用 Git 提交一次儲存成新版本。改變主意時，用一句話就能請 Claude 把 App 還原成最初的穩定版。

整段示範把前面所有觀念串起來：CLAUDE.md 收紀律、Plan Mode 收需求、Skills/MCP 補能力、Git 兜住安全網——這就是「動動嘴就能做出 Anything」在實務上真正的樣子。
