Skill 的本質不是新東西，而是把提示詞拆解、按能力打包、用時動態載入——這是把 prompt engineering 第一次做成真正的「工程」。在這條核心論點之下，作者鋪了四個支撐：

- **誰因此受益**：大模型上半場屬於演算法科學家，下半場是落地，軟體工程師反而變成「懂行的人」。
- **怎麼裝**：原則是「寧濫勿缺」——能找到的全裝，找不到的自己造（一句話的 markdown 也能算 skill），再逐步補步驟、補腳本、補案例。作者已裝約 300 個，並以資料視覺化、CVE 漏洞分析為例示範按需載入如何運作。

## 1. Skill 是 prompt engineering 的「依賴管理」時刻 (00:00)

業界三巨頭裡，OpenAI 最會炒作、Google 最會做演算法、Anthropic 最會做開發——繼 2024 年底的 MCP 之後，2025 年底 Anthropic 又丟出 Agent Skill。Skill 本身沒有什麼石破天驚的突破，甚至有點「返璞歸真」：它解決的是一個很現實的問題——**如何用最少的 token 辦最多的事**。答案就是把提示詞拆解、按能力範圍打包、彼此保留指針，然後實時按需匯入，做動態的提示詞構建。

之所以說 skill 是目前那麼多個 AI 應用概念裡最有機會成功的那個，是因為它讓人想起 maven、npm、crate、pip——大家熟悉的依賴管理。你可以罵現在的技術框架過於依賴依賴，一個 hello world 就要裝上千個依賴；但不可否認的是，正是這種積木結構帶來了無窮可能性。

從整合難度來看，skill 比大模型、MCP 都更低、接受度更高。大模型——天天更新的 VSCode 到現在還得靠第三方插件支援其他模型；MCP——尤其在去年一連串安全漏洞事故後，稍微專業一點的平台對 MCP 接入都加上了好幾層驗證機制（作者自述把 AWS 上一個 AI 服務接上 GitHub 的 MCP，從查資料到生成各種密鑰，搞了將近一個小時）。Skill 用最簡單的方法繞開了這些問題：**完全本地執行**，所有程式碼本地儲存、所有指令本地執行，一切公開透明，沒有跨網路通訊，自然也不會有 RPC 漏洞之類的安全問題。

也正因為這個結構，作者把 skill 的出現視為**第一次讓 prompt engineering 真正像一個「工程」**。在這之前，我們對提示詞的使用更像在做實驗——這邊給它一點酸、那邊給它一點鹼，再看大模型這個生物有什麼反應。

## 2. 下半場屬於軟體工程師：為何要把 300 個 skill 全裝進去 (01:27)

現在大模型對 function call 之類的基本機制已經穩定下來，skill 這種**有結構、有規模的軟體工程範式**才可能真正普及。對軟體工程師而言，這是一個契機：大模型迭代的上半場主角是演算法科學家，那些概念我們看都看不懂，只能乖乖當使用者；現在進入應用落地的下半場，軟體工程的理念會更發揮作用——我們反而變成了「懂行的那個」。

為了搞清楚目前的 skill 生態，作者跑遍網路、蒐集了大約 **300 個開源 skill**，涵蓋檔案處理、資料分析、網頁生成、安全檢測、專案管理等領域，全部裝進 IDE。由於現在還沒有 npm 那種包管理框架，這些 skill 還得一個個匯入，略嫌繁瑣。

為什麼一股腦全裝、而不是用什麼裝什麼？因為**你永遠不會知道什麼時候會需要用上什麼 skill**。這個直覺會在下一章的具體例子裡得到驗證。

## 3. 寧濫勿缺與漸進式造輪子：skill 的安裝與養成 (03:01)

以「讓 AI 做一個完整的資料視覺化專案」為例：AI 經過需求拆解、分析後，給出的設計方案包含——資料源用 CSV、視覺化框架用 D3.js、前端測試用 Playwright。**因為什麼都裝了，這些都有對應的 skill**，AI 就會在系統提示詞裡發現它們、直接到對應的 skill 裡匯入相關提示詞和參考程式碼。下一次方案如果換成用 Excel 當資料源、視覺化框架換成 echarts、測試改用 property-based testing，也不用著急——這些 skill 同樣已經就位。

這種**按需匯入的機制**，決定了安裝 skill 時要遵守「**寧濫勿缺**」的原則：能找到多少就裝多少，找不到的自己造——因為造 skill 比想像中容易得多。就像 Node.js 裡只有一行程式碼的工具包一樣，你的 skill 也可以只是一份**只有一句話的 markdown 文件**。

在這個最小骨架之上，再逐步擴展：加步驟、加可執行腳本、補更多案例。作者以自己前幾天做的 **CVE 漏洞分析 skill** 示範這個過程——一開始很簡單，只有三步：找到官方報告、提取出漏洞的程式碼和官方解釋、生成總結。後來陸續補上更細的拆解要求；在請它分析時，專門指出要關注哪些點，引導 AI 做更有針對性的解讀；再後來，把某些步驟綁定執行腳本——例如在收集官方報告時指定用什麼腳本爬網頁，以保證資料獲取的準確性。有了這個 skill 之後，平時問 AI 一些技術問題時，它就能給出更專業的回答；沒有 skill 的時候，AI 只會像播報新聞那樣，給一個很籠統的漏洞分析。

## 4. Skill 真正的價值是 token 可控——未來會分 Lite／Pro／Max (05:17)

作為實用主義者，作者認為 skill 最大的價值在於——**對輸入的 token 數量有了可控度**。沒有 skill 的時候，你完全無法控制 AI 為了完成一個小動作要爬多少外部網頁、匯入多少參考程式碼、燒多少 token；有了 skill 之後，你能精確控制每一個輸入字元：想要更細緻的操作，就多一點提示；想要輸出更穩定，就多一些參考案例；反過來，也可以在不影響輸出效果的前提下，適當削減提示詞、減輕 token 負擔。

這件事在當下的社群語境裡特別有感——粉絲群最近聽到最多的抱怨就是「token 額度又沒了」「基礎套餐完全不夠用」。作者自承是「羊毛黨」，連基礎套餐都不買，專挑免費的薅，不然 GPT、Gemini、Claude 這些國外大模型每一個燒的都是美元、又個個都是 token 吞噬者，實在耗不起。

由此他大膽推測：未來 skill 的發展會有點像大模型一樣，開始出現**分級分類**——例如更省 token 的 **Lite Skill**、提示詞更詳細的 **Pro Skill**、完全不差錢的 **Max Skill**。而像他這種羊毛黨，就會用著免費的 IDE、跑著最省錢的 Lite Skill，做個勤儉持家的好男人。
